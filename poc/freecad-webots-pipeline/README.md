# FreeCAD → Webots Pipeline POC (issue #24)

Standalone spike validating **only the pipeline mechanics** — FreeCAD STL→STEP
import/export, URDF authoring, and Webots URDF import/wheel-joint
articulation — using a public, already-rigged wheeled robot (TurtleBot3
Burger, ROBOTIS, Apache-2.0). Deliberately decoupled from this workspace's
own pendulum/wheel/servo geometry in `inverted-pendulum-project/03_Parts/Generators/`
(not touched by anything here).

**Result: end-to-end PASS.** Every stage completed successfully on this
run — no stop-rule triggering, no unresolved import failures. The pipeline
does surface one real fidelity gap worth carrying into #9/#10's design
(STEP round-trip volume/topology loss under the naive per-facet mesh
conversion pattern — see FINDINGS.md section 3). See the full write-up in
[`findings/FINDINGS.md`](findings/FINDINGS.md) and the asset attribution
record in [`NOTICE`](NOTICE).

Relates to #9 (this project's own URDF export design) and #10 (this
project's own Webots import) — this POC exists to de-risk those before real
project geometry has to carry that risk.

## Layout

```
poc/freecad-webots-pipeline/
  00_fetch_turtlebot3_assets.sh   Stage 0 — fetch pinned-SHA TurtleBot3 assets
  reference/                      gitignored — fetched by the script above
  freecad/
    01_import_and_export_step.py  Stage 1 — Mesh -> Part.Shape -> STEP (headless FreeCAD)
    01_import_and_export_step.sh  FREECAD_BIN wrapper for the above
    02_roundtrip_check.py         Stage 1b — re-import STEP, diff vs source, re-export mesh
    output/                       gitignored — generated per run
  urdf/
    turtlebot3_poc.urdf           Stage 2 — hand-authored POC URDF
    meshes/                       gitignored — copied from freecad/output/ (see Stage 2 below)
  webots/
    worlds/turtlebot3_poc.wbt     Stage 3 — hand-authored world (committed), EXTERNPROTOs the generated PROTO below
    protos/                       Stage 3 — PROTO generated by urdf2webots (gitignored)
    controllers/wheel_articulation_check/wheel_articulation_check.py
    _provision_assets.sh          shared Stage 0/1/1b/3 auto-provisioning, sourced by both scripts below
    run_batch.sh                  runs the generated world in --batch --mode=fast
    run_gui.sh                    runs the generated world live (--mode=realtime, GUI) — see "Watching it live" below
  findings/
    FINDINGS.md                   Stage 4 write-up (feeds #9 Stage 4 and #10)
```

## Why assets aren't committed

Per the issue #24 plan, TurtleBot3 assets are fetched on demand and
gitignored rather than committed: acquisition is pinned to an exact commit
SHA (see below), so a fetch is fully reproducible, and this avoids growing
the repo with vendored STL/mesh binaries (this repo's `.git` is already
sensitive to STL bloat — see #9's notes on `03_Parts/Generators/`).

The generated Stage 1 STEP files, Stage 1b round-tripped mesh re-exports,
and the Stage 3 `urdf2webots`-generated PROTO are likewise gitignored
(`freecad/output/`, `urdf/meshes/`, `webots/protos/`) — all reproducible by
re-running the stages below.

`urdf/turtlebot3_poc.urdf` and `webots/worlds/turtlebot3_poc.wbt` **are
committed** — both are small, hand-authored text files meant to be
read/reviewed directly (the URDF's `<mesh>` filenames point at
`urdf/meshes/`, which you regenerate locally — see Stage 1b; the world
file's `EXTERNPROTO` points at `webots/protos/TurtlebotPoc.proto`, which you
regenerate via `urdf2webots` — see Stage 3). Only the *generated* PROTO
(with its mesh-copying textures directory) is gitignored, not the world
that references it.

## Reproducing end to end

Requires: headless FreeCAD 1.1.3 (`FREECAD_BIN`, e.g.
`~/.local/opt/freecad-1.1.3/usr/bin/freecadcmd`), Webots R2025a
(`/usr/local/bin/webots`), and the `pendulum-tools` mamba env with
`urdf2webots` installed (`mamba run -n pendulum-tools pip install urdf2webots`).

### Stage 0 — fetch assets

```bash
cd poc/freecad-webots-pipeline
./00_fetch_turtlebot3_assets.sh
```

Fetches `turtlebot3_burger.urdf` + `burger_base.stl` + `left_tire.stl` +
`right_tire.stl` from `ROBOTIS-GIT/turtlebot3` at the pinned SHA recorded in
the script (re-resolved once via `git ls-remote` at implementation time —
see the script header for how to deliberately re-pin), verifies the LICENSE
at that SHA is Apache-2.0, and writes/refreshes `NOTICE`.

### Stage 1 — FreeCAD import & STEP export

```bash
export FREECAD_BIN=~/.local/opt/freecad-1.1.3/usr/bin/freecadcmd
./freecad/01_import_and_export_step.sh
```

Imports each of `burger_base.stl`, `left_tire.stl`, `right_tire.stl` as a
`Mesh.Mesh`, converts to a `Part.Shape` (per-facet `makePolygon`/`Face` →
`makeShell`/`makeSolid`, same pattern as
`inverted-pendulum-project/03_Parts/Generators/01_convert_servo_stl_to_step_via_freecad.py`),
and exports STEP files into `freecad/output/`. Writes
`freecad/output/stage1_conversion_report.json`.

**Performance note:** `burger_base.stl` has ~96.5k facets — see FINDINGS.md
for concrete timing at this facet count with the naive per-facet conversion
pattern (it is meaningfully slower than the ~35.7k-facet servo mesh this
pattern was originally built around; treat this as a real data point for
#9's own mesh sizes, not something this POC pre-optimizes around).

### Stage 1b — STEP round-trip check

```bash
"$FREECAD_BIN" -c "__file__=r'$(pwd)/freecad/02_roundtrip_check.py'; exec(open(__file__).read())"
```

Re-imports each STEP file, diffs bbox/volume/facet-count against the source
mesh, writes `freecad/output/roundtrip_report.json`, and re-exports each
round-tripped shape as an STL (`freecad/output/<link>_roundtrip.stl`).

Then copy the round-tripped re-exports where the POC URDF expects them:

```bash
mkdir -p urdf/meshes
cp freecad/output/burger_base_roundtrip.stl urdf/meshes/
cp freecad/output/left_tire_roundtrip.stl urdf/meshes/
cp freecad/output/right_tire_roundtrip.stl urdf/meshes/
```

(Per decision #4 in the approved plan, `urdf/turtlebot3_poc.urdf` references
these FreeCAD round-tripped re-exports, not the pristine vendored STLs in
`reference/meshes/` — this exercises FreeCAD's own mesh-export path, which
is the actual point of the spike.)

### Stage 2 — POC URDF

`urdf/turtlebot3_poc.urdf` is already hand-authored and committed — a
structural copy of the fetched reference URDF, with `base_link` as the
root link directly (see issue #32 — the reference URDF's massless
`base_footprint` root + fixed `base_joint` were dropped, since that
structure left the generated Webots PROTO's `Robot` node without its own
`physics`/`boundingObject`); `wheel_left_joint`/`wheel_right_joint` as
`type="continuous"`, `axis="0 0 1"`, `origin rpy="-1.57 0 0"`; fixed
`caster_back_joint` with a box-collision-only `caster_back_link`, no
mesh — matching the real ROBOTIS URDF). Nothing to run for this stage
beyond the mesh copy above.

This URDF is **not** produced by, and does not feed into, issue #9's future
`urdf_builder.py` / `10_export_urdf.py` exporter — it's hand-maintained for
this POC only.

### Stage 3 — Webots import & articulation test

Baseline sanity check (independent of this POC, confirms the local Webots
install/EXTERNPROTO resolution works at all):

```bash
webots --batch --mode=fast --stdout --minimize \
  /usr/local/webots/projects/robots/robotis/turtlebot/worlds/turtlebot3_burger.wbt
```

Convert the POC URDF to a Webots PROTO:

```bash
mamba run -n pendulum-tools pip install urdf2webots   # one-time, into pendulum-tools
mamba run -n pendulum-tools python3 -m urdf2webots.importer \
  --input=urdf/turtlebot3_poc.urdf \
  --output=webots/protos/TurtlebotPoc.proto \
  --target=R2025a
```

Then run the (already-committed) world and articulation check:

```bash
./webots/run_batch.sh webots/worlds/turtlebot3_poc.wbt
```

Per issue #28, `turtlebot3_poc.wbt` uses the standard Webots library
PROTOs (`TexturedBackground`, `TexturedBackgroundLight`, `RectangleArena`)
for a more polished viewpoint/background/arena instead of hand-rolled
nodes. In addition to the local `../protos/TurtlebotPoc.proto`
`EXTERNPROTO`, this means the first Webots launch after a fresh checkout
needs network access to resolve those three `EXTERNPROTO`s from
`raw.githubusercontent.com` — Webots caches them locally after that, so
subsequent runs don't need network access.

`webots/controllers/wheel_articulation_check/wheel_articulation_check.py`
commands both wheel motors to a fixed velocity, steps the simulation a
handful of times, and reports pass/fail based on whether the wheel joint
position sensors actually moved.

**Result on this run:** succeeded on the first attempt — no import errors,
device names matched the URDF joint names exactly
(`wheel_left_joint`/`wheel_right_joint` plus auto-added
`<name>_sensor` position sensors), and both wheels visibly rotated under
the commanded velocity (`VERDICT: PASS`). See FINDINGS.md section 6 for the
full console output and section 7 for the stop-rule outcome (not
triggered).

## Watching it live

The stages above (via `run_batch.sh`) run Webots headless/batch
(`--batch --mode=fast --no-rendering --minimize --stdout`) — no window is
ever shown. To actually watch the robot drive in the Webots GUI:

```bash
./webots/run_gui.sh webots/worlds/turtlebot3_poc.wbt
```

This launches `webots --mode=realtime "$WORLD"` (no batch/headless flags) —
press Play in the Webots window if the simulation starts paused.

On a fresh `main` checkout the generated assets this world needs
(`reference/`, `freecad/output/`, `urdf/meshes/`, `webots/protos/` — all
gitignored, see "Why assets aren't committed" above) don't exist yet. Both
`run_gui.sh` and `run_batch.sh` auto-provision them, via the shared
`provision_assets` function in `webots/_provision_assets.sh`: it checks for
`webots/protos/TurtlebotPoc.proto` and its upstream prerequisites (each
checked for being non-empty, not just present, so a truncated artifact from
an interrupted prior run isn't mistaken for a finished one), and if
anything is missing it runs Stage 0 (`00_fetch_turtlebot3_assets.sh`),
Stage 1/1b (FreeCAD STEP export + round-trip, via `FREECAD_BIN`), and
Stage 3 (`urdf2webots`, via the `pendulum-tools` mamba env) in order before
launching Webots — the same scripts documented above, just invoked for you
instead of failing fast. It prints progress per stage; Stage 1's STEP
conversion is the slow part (~74s for `burger_base` alone — see
FINDINGS.md), so first-run provisioning takes a couple of minutes.
`FREECAD_BIN` and `WEBOTS_BIN` follow the same conventions as elsewhere in
this POC (see Stage 1/Stage 3 above). If assets are already present (e.g.
from a prior run), provisioning is skipped and Webots launches immediately.
Because the provisioning logic lives in one shared script, `run_batch.sh`
on a fresh checkout now auto-provisions too, instead of the old fail-fast
"World file not found" behavior — its headless invocation itself
(`--batch --mode=fast --no-rendering --minimize --stdout`, with the
`xvfb-run` fallback) is unchanged.

Both scripts fail fast, before touching the pipeline, if `$WORLD` doesn't
exist or `WEBOTS_BIN` isn't a runnable binary — no point burning a
multi-minute provisioning run on either. `provision_assets` itself also
checks `mamba` is on `PATH` up front (Stage 3's dependency, but knowable
before Stage 0/1/1b run) and, if the given `$WORLD` doesn't reference the
generated `TurtlebotPoc` PROTO at all (checked via its `EXTERNPROTO`
declaration), skips provisioning entirely rather than regenerating a PROTO
an unrelated world doesn't need.

`run_gui.sh` requires a real `DISPLAY` and, unlike `run_batch.sh`, does
**not** fall back to `xvfb-run` on a display error — Xvfb has no visible
framebuffer, so that fallback would silently defeat the entire point of
this script. If `$DISPLAY` is unset, it fails immediately with a clear
message instead.

### Short demo window and motor persistence

`wheel_articulation_check.py` commands both wheel motors, runs for ~300
simulation steps (~10s simulated at the world's 32ms time step), printing
wheel position/velocity telemetry every 25 steps, then prints its
PASS/FAIL verdict and exits — the controller process itself does not keep
running indefinitely.

Webots' documented behavior is that motor targets persist after the
controller disconnects — i.e. the wheels should keep spinning at the last
commanded velocity even after the controller process exits and the
console output stops. This is the expected behavior on this build, **but
it was not independently re-verified live** (see issue #26's own
"optional, opportunistic" framing of that spot-check; this implementation
did not pop a Webots window on this machine's real, currently-active
`DISPLAY=:1` desktop session without being asked to).

The world's floor is a flat, wall-less 2×2m plane (see
`webots/worlds/turtlebot3_poc.wbt`), so if the wheels do keep turning after
the controller exits, the robot will eventually drive off the edge of the
floor — that is expected given the world geometry, not a sign of a stall
or crash. If you run `run_gui.sh` and watch this happen, please note what
you actually observed (does the robot keep moving after the console output
stops, or does it stop with the controller?) in the PR/issue thread — that
closes out the one open item this issue deliberately left for a human.

## Stop-rule note

Per decision #6 in the approved plan: if Stage 3 Webots URDF import failed
3 times with genuinely distinct fixes attempted, the plan was to stop there
and document the failure itself as the Stage 4 finding rather than keep
iterating. **This did not happen on this run** — Stage 3 import and the
articulation test both passed on the first attempt. See FINDINGS.md
section 7.
